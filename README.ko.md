# 연합학습에서 양자화와 데이터 이질성은 서로를 악화시키는가

> 클라이언트 메모리 제약 때문에 모델을 양자화해야 하고, 동시에 기기마다 데이터 분포가 다른 상황.
> 이 두 악조건이 **곱해지는지(상호작용)** 아니면 **더해지기만 하는지**를 24개 실험으로 측정했습니다.

**결론: 더해지기만 합니다.** 양자화의 성능 대가는 데이터 이질성을 1000배 바꿔도 일정했습니다.
다만 이 null 결과는 **설계상 상호작용이 나타나기 어려운 조건이었다는 점**을 함께 보아야 합니다(→ [회고](#8-회고--무엇이-잘못되었나)).

| | |
|---|---|
| 기간 / 규모 | 6주 · 24개 학습 실행 · 33.7 GPU-시간 (NVIDIA A10G) |
| 모델 / 데이터 | Qwen2.5-0.5B-Instruct · databricks-dolly-15k (15,011건) |
| 스택 | PyTorch · Flower · PEFT · bitsandbytes · Transformers |
| 산출물 | 보고서, 연구기록 문서, 발표자료, 재현 가능한 로그·스크립트 |

---

## 1. 문제 정의

학습 데이터를 한곳에 모을 수 없는 상황이 늘고 있습니다. 병원 기록, 휴대폰의 입력 데이터처럼
기기 밖으로 내보낼 수 없는 데이터가 그렇습니다. **연합학습(Federated Learning)**은 데이터를
모으는 대신 모델을 각 기기로 보내 학습시키고, 결과만 합칩니다.

그런데 실제 클라이언트는 데이터센터가 아닙니다. 두 가지 제약이 동시에 걸립니다.

```
제약 1: 메모리가 부족하다        →  모델을 양자화해서 올린다 (QLoRA)
제약 2: 기기마다 데이터가 다르다  →  클라이언트 업데이트가 서로 어긋난다 (client drift)
```

각각의 해법은 잘 알려져 있습니다. 모르는 건 **둘이 겹칠 때 무슨 일이 일어나는가**입니다.

정밀도를 깎은 모델은 수치적 여유가 적으니, 서로 충돌하는 업데이트를 더 못 버틸 수 있습니다.
그렇다면 양자화의 대가는 데이터가 불균등할수록 커질 것입니다. **이것이 검증하려던 가설입니다.**

실무적으로 중요한 이유는 분명합니다. 상호작용이 있다면 압축 수준을 정할 때
사용자 데이터 분포를 알아야 하는데, 배포 시점에 그걸 아는 경우는 거의 없습니다.
없다면 압축은 **하드웨어만 보고** 정하면 됩니다.

## 2. 연구질문과 가설

> **RQ.** 동결 base 모델을 양자화할 때 생기는 성능 손실이, 클라이언트 데이터가
> 비균등해질수록 커지는가?

**H1 (작업가설):** 양자화 오차와 클라이언트 드리프트는 상호작용한다. 즉 Dirichlet α가
작아질수록(비균등해질수록) 양자화 페널티가 증가한다.

## 3. 실험 설계

### 3.1 요인 설계 — 3 × 2 × 4 = 24조합 전수

| 요인 | 수준 | 선택 이유 |
|---|---|---|
| **압축** | 무압축(bf16) / INT8 / NF4 4bit | 양자화 강도를 3단계로. 8bit는 중간 지점 |
| **FL 알고리즘** | FedAvg / FedProx(μ=0.01) | 드리프트 교정 유무 비교 |
| **데이터 이질성** | Dirichlet α = 0.1 / 1 / 10 / 100 | 1000배 범위. α=100은 near-IID 끝점 |

일부 조합만 돌리지 않고 **전수 설계**를 택한 이유는, 상호작용을 보려면 격자 전체가
필요하기 때문입니다. 대신 모델 크기를 0.5B로 낮춰 예산 안에 넣었습니다
(3B → 1.5B → 0.5B로 두 차례 축소).

### 3.2 파티셔닝이 실제로 만드는 분포

카테고리별 Dirichlet 추출(seed 42)로 8개 클라이언트에 분배했습니다.

| | α = 0.1 | α = 100 |
|---|---|---|
| 클라이언트별 최다 카테고리 비중 | **66%** | 25% |
| 샤드 크기 범위 | 119 ~ 3,047건 | 1,645 ~ 1,773건 |

α=0.1에서는 한 클라이언트가 `open_qa`만 99% 받는 식으로 극단적으로 쏠립니다.

### 3.3 학습 설정

```yaml
클라이언트: 8대, 매 라운드 전원 참여(fraction_fit=1.0)
PEFT:      LoRA r=8, α=16, dropout 0.05, target=[q_proj, v_proj]
           → 학습 파라미터 540,672개 (전체의 0.11%)
최적화:    AdamW, lr 2e-4, micro-batch 4 × accum 4 (유효 16), max_len 512
라운드:    최대 10, "3라운드 연속 개선률 <1%"면 조기 종료
평가:      서버가 held-out 1,497건으로 매 라운드 PPL
           ROUGE-L은 마지막 라운드에 층화표본 200건 1회
```

**평가를 서버에서 수행**한 것은 지도교수 피드백을 반영한 변경입니다. 이전에는 대표
클라이언트를 통해 평가했는데, 데이터가 전역 공유 held-out이라 값은 같지만
"서버가 평가한다"는 구조를 코드로 드러내는 편이 맞다는 지적이었습니다.

### 3.4 측정 지표 — 네 축

| 축 | 지표 |
|---|---|
| 성능 | `val_loss`, `val_perplexity`, `rouge_l` |
| 속도 | `round_latency_sec`, 수렴 라운드 수 |
| 메모리 | `peak_vram_gb` |
| 통신 | `communication_bytes_this_round` |

압축이 한 축에서 이득을 주면서 **다른 축에서 대가를 요구**할 수 있다고 보고 의도적으로
네 축을 모두 기록했습니다. 결과적으로 이 선택이 가장 유용한 발견(8bit 속도 역전)을 만들었습니다.

## 4. 구현

```
src/
  models.py        LoRA / QLoRA(8bit·4bit) 배선, 단일 get_model(config) 진입점
  data.py          Dolly-15k 로딩, held-out 분리, 토크나이즈(프롬프트 라벨 마스킹)
  partitioning.py  카테고리별 Dirichlet 비IID 분배
  fl_client.py     로컬 학습, FedProx proximal term, VRAM·지연 계측
  fl_runner.py     라운드 루프(fit→집계→평가→체크포인트→수렴판정)
  evaluate.py      PPL·ROUGE-L 평가, 상호작용 분석 함수
  scaffold.py      SCAFFOLD(core 설계에서 제외, 코드·테스트는 유지)
scripts/
  run_experiment.py / run_alpha100.sh / analyze_interaction.py / plot_results.py
tests/             12개 파일, 66개 테스트
```

### 설계 판단 몇 가지

**Flower의 `start_simulation()`을 쓰지 않고 라운드 루프를 직접 구현했습니다.**
고정 라운드 수만 돌 수 있어 수렴 기준에 따른 조기 종료나 체크포인트 재개가 어려웠기
때문입니다. 스팟 인스턴스가 회수돼도 이어서 돌 수 있어야 했습니다.

**토크나이즈에서 프롬프트를 앞에서 자릅니다.** 전체 텍스트를 뒤에서 자르면
context가 긴 카테고리(closed_qa, summarization)는 응답이 통째로 날아가
라벨이 전부 -100이 됩니다. 이게 실제로 NaN 손실을 일으켰습니다(→ [7절](#7-발견하고-고친-문제들)).

**체크포인트를 매 라운드 저장**하고 재시작 시 자동 재개합니다.

## 5. 진행 과정

| 주차 | 한 일 |
|---|---|
| 1 | 모델·GPU 환경 확인, PEFT 배선(LoRA/QLoRA/DoRA) |
| 2 | Dolly-15k 파이프라인, Dirichlet 파티셔닝 |
| 3 | FedProx·SCAFFOLD, 체크포인트, 수렴 기준, FL 통합 테스트 |
| 4 | 실험 러너·분석 함수 구현, GPU에서 18조합 실행 |
| 5 | 지도교수 피드백 반영 설계 개정, 서버 평가 전환, α=100 추가 실행 |
| 6 | 24조합 분석, 그림·보고서·발표 |

### 설계가 바뀐 지점

중간에 세 번 설계를 고쳤고, 각 변경의 근거를 커밋 메시지에 남겼습니다.

1. **연구 초점 재설정** — 3FL×2PEFT(6조합)에서 **3압축×2FL×3α(18조합)**으로.
   "압축률과 non-IID 강도의 상관관계"를 중심축으로 삼으라는 피드백.
2. **평가 주체 변경** — 클라이언트 경유 평가 → 서버 직접 평가.
3. **α=100 추가** — near-IID 끝점이 필요하다는 피드백으로 18 → 24조합.

주차별 브랜치(`week1`~`week6`)에 각 시점 코드가 그대로 보존돼 있어,
어느 결과가 어느 코드에서 나왔는지 추적할 수 있습니다.

## 6. 결과

### 6.1 압축의 주효과 — 명확하고 단조적

LoRA 대비, (FL × α) 8셀을 짝지어 비교한 값입니다.

| | PPL 악화 | ROUGE-L 변화 | 8칸 중 하락 |
|---|---|---|---|
| QLoRA 8bit | **+0.55%** (−0.56 ~ +1.02) | −0.0034 | 5칸 (3칸은 상승) |
| QLoRA 4bit | **+5.74%** (5.29 ~ 6.33) | −0.0141 | **8칸 전부** |

8bit는 셀마다 **부호가 바뀝니다** — 실제 효과가 아니라 측정 노이즈라는 뜻입니다.
4bit는 8칸 전부에서 같은 방향입니다. 측정 원리가 다른 두 지표(teacher-forcing 기반 PPL,
실제 생성 기반 ROUGE-L)가 독립적으로 같은 결론을 냈습니다.

### 6.2 상호작용 — 찾지 못했습니다 (핵심 결과)

4bit의 PPL 악화를 α별로 늘어놓으면:

| α | 0.1 | 1 | 10 | 100 |
|---|---|---|---|---|
| 4bit | 5.66% | 5.57% | 5.94% | 5.79% |
| 8bit | 0.72% | 0.19% | 0.54% | 0.73% |

**1000배 범위에서 변동폭 0.37%p.** 이게 의미 있는 크기인지 판단하려면 노이즈 기준이
필요한데, 8bit가 그 역할을 합니다. 8bit는 성능 손실이 없는 조건인데도
8칸에서 −0.56% ~ +1.02%(폭 1.58)로 흩어집니다. **압축 페널티는 효과가 없다고 알려진
값보다도 좁게 움직였습니다.**

방향도 가설과 반대입니다. 가장 큰 4bit 페널티는 **α=100(가장 균등한 쪽)**에서 나왔습니다.

3원 분산분해로도 같은 결론입니다. 압축이 전체 변동의 **89.6%**, 압축×α 상호작용은
**0.2%**이고 F=0.15로 **잔차보다 작습니다**.

### 6.3 예상 밖의 발견 — 8bit는 품질 손실 없이 2.2배 느립니다

| | VRAM | 라운드당 시간 | PPL 악화 |
|---|---|---|---|
| LoRA | 14.44 GB | 11.7분 | 기준 |
| **8bit** | 12.25 GB (−15%) | **25.5분 (2.19배)** | +0.55% |
| 4bit | 10.07 GB (−30%) | 12.4분 (1.07배) | +5.74% |

메모리 1GB를 아끼는 대가가 두 단계에서 10배 다릅니다.

```
LoRA → 8bit :  −2.20GB,  PPL +0.25%p/GB,  라운드당 +13.8분
8bit → 4bit :  −2.18GB,  PPL +2.39%p/GB,  라운드당 −13.1분
```

원인은 bitsandbytes의 `LLM.int8()`이 정확도를 지키려고 **매 행렬곱을 outlier 경로와
int8 경로로 쪼개 계산**하기 때문입니다. 이 고정 비용은 행렬 크기와 무관해서,
0.5B처럼 연산 자체가 가벼운 모델에서 비중이 커집니다. 실제로 라이브러리 버전이
다른 환경에서는 1.85배로 줄었습니다.

**정확도만 보면 8bit가 최선의 절충처럼 보이지만, 시간 축을 넣으면 결론이 뒤집힙니다.**

### 6.4 양자화는 통신량을 줄이지 않습니다

24개 런 전부 라운드당 **17,301,504 바이트로 동일**했습니다.

```
LoRA 어댑터 540,672개 × 4바이트(fp32) = 2.16MB  (클라이언트 1대)
2.16MB × 8대 = 17.3MB                           (라운드당)
```

QLoRA가 양자화하는 건 **전송하지 않는 동결 base 모델**이고, 전송되는 어댑터는
fp32 그대로이기 때문입니다. FL 문헌의 "quantisation reduces communication"은
전송되는 업데이트를 양자화하는 이야기로, **이 실험이 조작한 축과 다릅니다**(→ [8절](#8-회고--무엇이-잘못되었나)).

### 6.5 FedProx는 12셀 전부에서 FedAvg보다 나빴습니다

PPL 평균 +1.51% 악화, ROUGE-L도 12셀 중 11셀에서 하락. 수렴 라운드(5.25 vs 5.08)나
시간·메모리에서 얻는 이득은 없었습니다. 다만 μ를 튜닝하지 않았으므로
**"μ=0.01이 이 설정에 맞지 않았다"와 구별되지 않습니다**.

## 7. 발견하고 고친 문제들

결과 자체만큼이나 과정에서 잡은 것들이 있습니다.

**① NaN 손실 — 라벨이 전부 마스킹되던 버그**
프롬프트+응답을 뒤에서 자르다 보니, context가 긴 예제는 응답이 통째로 사라져
라벨이 전부 -100이 됐습니다. 그런 예제가 한 미니배치에 몰리면 loss 분모가 0이 되어
NaN이 나고, FedAvg 집계를 거쳐 전역 모델 전체가 오염됩니다. α=0.1 파일럿에서 재현했고,
**프롬프트 앞부분을 자르는 방식**으로 바꿔 차단했습니다.

**② 완료된 런 6개가 "없음"으로 보고되던 문제**
분석 스크립트는 α를 정수로 들고 있어 `_a10`을 찾는데, 실행기는 float로 받아
`_a10.0`으로 저장하고 있었습니다. 에러 없이 **조용히 12/18만 완료됐다고 보고**했습니다.
양쪽 `build_run_name()`을 `float(alpha)`로 정규화해 해결했습니다.

**③ 아카이브와 체크섬 매니페스트 불일치**
Zenodo 배포본의 `MANIFEST.sha256`은 로그 48개를 목록화했는데 실제로는 12개만 들어 있었고,
반대로 "재생성 가능하므로 제외한다"고 문서화한 체크포인트 138MB가 포함돼 있었습니다.
누락분을 채우고 체크포인트를 제거해 141.6MB → 9.6MB로 정리했습니다.

**④ 환경 혼입 감지**
α=100 6개 런만 다른 소프트웨어 스택에서 돌았다는 사실을, **8bit 라운드 시간이
25.5분에서 21.6분으로 바뀐 것**에서 역으로 발견했습니다. 이후 시간 비교는
같은 환경의 18런으로 제한했습니다.

테스트는 66개(데이터 준비, 파티셔닝, 어댑터 배선, 집계, 체크포인트, 수렴 기준, 분석 함수)이며
각 실험 전에 통과를 확인했습니다.

## 8. 회고 — 무엇이 잘못되었나

포트폴리오로서 가장 중요한 절이라고 생각합니다. 결과를 변호하기보다 **설계를 진단**합니다.

### ① 드리프트를 최소화한 설정에서 드리프트 상호작용을 찾았습니다

가설의 기전은 "양자화된 모델이 **클라이언트 드리프트**를 잘 흡수하지 못한다"입니다.
그런데 드리프트는 동기화 사이의 로컬 연산량에 비례해 커지는데:

```
local_epochs = 1      ← 1에폭 돌고 바로 집계
fraction_fit = 1.0    ← 8대 전원 매 라운드 참여
수렴 5~7 라운드        ← 전체 학습 개선의 71%가 라운드 1→2에서 끝남
```

로컬 1에폭 + 전원 참여는 FedAvg를 사실상 큰 배치 SGD에 가깝게 만듭니다.
실제로 **non-IID의 주효과 자체가 라운드1 +0.147 PPL에서 최종 +0.024로 거의 사라집니다.**
거의 사라진 효과를 양자화가 증폭할 여지는 없습니다.

**즉 이 null은 양자화에 대한 발견이라기보다 설계의 귀결에 가깝습니다.**

### ② 드리프트를 한 번도 측정하지 않았습니다

라운드별로 남긴 건 전역 지표(loss, PPL, 시간, 통신량, VRAM)뿐입니다.
클라이언트 간 업데이트의 코사인 유사도, 노름 분산, 전역 모델로부터의 이탈 거리 —
**하나도 기록하지 않았습니다.** 그래서 "양자화 오차는 공유 편향이고 드리프트는
어댑터에서 발생하므로 둘이 독립적"이라는 해석은 **검증할 수단 자체가 없었습니다.**

### ③ 연구질문과 조작한 변수가 어긋나 있었습니다

문헌에서 "compression × non-IID" 상호작용이 보고되는 compression은 **통신 압축**
(전송되는 업데이트의 양자화·희소화)입니다. 이 실험이 조작한 건 **메모리 압축**
(동결 base 모델의 양자화)입니다. 측정하려는 개념과 조작한 변수가 다른
construct validity 문제입니다.

### ④ 통계적 근거가 약합니다

24조합 각 1회. 분산분해의 오차항은 반복이 아니라 **3원 상호작용을 노이즈로 가정**해
만든 것입니다. 파티션 시드도 42 고정이라 같은 α의 런들은 동일한 분할을 공유합니다.

### ⑤ 그 외

| 항목 | 문제 |
|---|---|
| 라운드 수 | 조건마다 5/6/7로 달라, 최종값 비교에 학습량이 섞임 |
| FedProx | μ=0.01 하나만 시험 → 알고리즘 열세로 단정 불가 |
| VRAM | GPU 한 장에 모델 9개 올린 값. 기기 1대 기준으로는 4~7% 추정 |
| 통신량 | 업로드만 집계 → 실제 왕복의 절반 |
| 모델 규모 | 0.5B. 활성값이 메모리를 지배해 양자화 이득이 작게 나옴 |

### 다시 설계한다면

```
1. 드리프트를 키운다       local_epochs 5~10, 참여율 낮추기(fraction_fit < 1)
2. 드리프트를 측정한다     라운드별 클라이언트 업데이트 간 코사인 유사도·노름 분산 로깅
3. 압축 대상을 바꾼다      base가 아니라 전송되는 어댑터를 양자화 → 문헌과 같은 축
4. 시드 3회 반복          가정된 오차항 대신 실측 오차
5. 고정 라운드 비교 추가   조기 종료와 별개로 동일 라운드 시점 비교
6. μ 스윕                FedProx를 공정하게 평가
```
